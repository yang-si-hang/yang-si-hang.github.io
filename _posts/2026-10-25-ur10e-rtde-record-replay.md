把一段 30 Hz 的机械臂示范插值到 300 Hz，再以更高频率发送，回放应该会更平滑、更接近原轨迹吗？

在这次 UR10e 实机实验中，答案是否定的。直接以 30 Hz 回放 dataset action 时，实际 TCP 轨迹相对原始示范晚约 **21 ms**；把同一组 action 做 10 倍插值并以 300 Hz 发送后，延迟反而增加到 **38 ms**。只有把插值目标从当前帧 `a[k]` 改为下一帧 `a[k+1]`，延迟才下降到 **4 ms**。如果保留遥操作过程中约 500 Hz 的原始 `sent_action` 及发送间隔，回放与原始轨迹之间没有检测到明显的额外延迟，未平移位置 RMSE 为 **0.095 mm**。

这个结果说明，回放频率本身不是决定因素。更关键的问题是：**一条 action 在数据中代表哪个时刻的目标，以及回放程序准备在什么时候完整执行它。**

![四种回放方式与原始 RTDE actual 轨迹的 XYZ 对比]({{ '/assets/img/posts/ur10e-rtde-replay/all-replays-xyz.png' | relative_url }})

_四种回放的实际 TCP 轨迹整体都很接近；不放大时间轴时，几十毫秒的差异并不容易直接看出。图中没有扣除拟合延迟。_

## 先分清三条数据链路

原始示范是一个 335 帧、30 Hz 的 LeRobot episode，持续约 11 秒。录制过程中实际上同时运行了三条频率和时间语义不同的链路。

第一条是约 500 Hz 的遥操作控制。程序读取 UR observation 和 Sigma 输入，计算目标，再调用 `send_action`。`recording/control.csv` 保存了发送前 observation、请求目标、经过适配层处理后真正提交的 `sent_action`，以及每次读取和发送的主机时间。

第二条是约 500 Hz 的 RTDE 记录。它直接订阅机器人控制器报告的 `actual_TCP_pose` 和 `target_TCP_pose`。这条链路使用控制器时间，与外部遥操作日志不是同一数据流。

第三条才是 30 Hz dataset 采样。每个 dataset 帧从最近成功完成的控制步中取一对 observation 和 `sent_action`，再从两台相机的缓冲区中读取最新图像。采样得到的 state 并不是一次新的 30 Hz 硬件测量；它仍然来自高频控制步发送 action 之前读取的反馈。图像也只是采样时拿到的最新缓冲帧，因此 dataset timestamp 不能直接当作曝光时间。

| 数据          | 记录内容                                     | 主要时间来源               |
| ------------- | -------------------------------------------- | -------------------------- |
| 高频控制日志  | observation、requested action、`sent_action` | 主机单调时钟               |
| RTDE 日志     | `actual_TCP_pose`、内部 `target_TCP_pose`    | 机器人控制器时间           |
| 30 Hz dataset | 抽取的 state/action 与最新相机帧             | dataset 采样时间与控制序号 |

这一区分决定了后面的比较口径。dataset action 是外部控制目标的采样结果，不是 RTDE 内部 `target_TCP_pose` 的降采样；两者即使数值接近，也不能视作同一个信号。

## 四种回放方式

为了判断误差来自低频采样、插值方法还是控制动态，我比较了四种回放方式。每次运行都先使用 `moveL` 到达原始首帧位姿，再开始正式发送 action。

| 回放方式          | 输入与发送方式                       |             指令数量与频率 |
| ----------------- | ------------------------------------ | -------------------------: |
| 30 Hz 原样回放    | 直接发送 `a[k]`，帧间零阶保持        |              335 条，30 Hz |
| 300 Hz 插值       | 对 `a[k]` 做 10 倍推理式插值         |            3350 次，300 Hz |
| 300 Hz 下一帧插值 | 改用 `a[k+1]` 作为当前周期目标       |            3340 次，300 Hz |
| 原始高频回放      | 回放原始 `sent_action`，保留发送间隔 | 5531 条，平均约 496.853 Hz |

两种 300 Hz 回放都对 XYZ 和夹爪做线性插值，对姿态做 SLERP。每个周期从实测 state 起步，在周期末完整提交目标。区别只在于这个目标是当前 dataset action `a[k]`，还是下一条 action `a[k+1]`。下一帧版本没有补齐最后一帧。

原始高频组则不做插值，也不移动标签。它直接取 dataset 首末帧关联的控制序号范围，重放其中连续的 5531 条 `sent_action`，并保留原始发送时刻之间的间隔。

## 用原始 RTDE actual 作为唯一参考

如果一组实验有时和 dataset state 比，有时又和 RTDE state 比，最终数字很难横向解释。因此这里将四次回放全部与原始示范的 RTDE `actual_TCP_pose` 比较，不用 dataset state 参与延迟评分。

设原始 RTDE 实际轨迹为 $S(t)$，某次回放的实际轨迹为 $R(t)$。分析在共同覆盖的约 0.5～10.93 秒区间内进行：位置线性插值到 2 ms 网格，姿态使用 SLERP；前 0.5 秒启动段被排除。随后在 $[-300,300]$ ms 范围内，以 1 ms 步长寻找

$$
\tau^*=\underset{\tau}{\operatorname{argmin}}\;
\operatorname{mean}\left(\left\|S_{xyz}(t)-R_{xyz}(t+\tau)\right\|^2\right).
$$

正的 $\tau$ 表示回放实际轨迹更晚。所有候选延迟都使用相同的 5215 个参考点，避免因为支撑区间变化而得到偏置结果。分析还分别检查 XYZ 三轴、速度有限差分相关性，以及 2 秒滑动窗口中的局部延迟。

这里同时报告两种误差：

- **未平移 RMSE**：原始与回放在相同相对时刻直接比较，反映实际复现效果；
- **平移后 RMSE**：扣除最佳拟合时间差后比较，主要反映轨迹形状是否一致。

后者可以帮助诊断，但不能替代前者。如果先把几十毫秒的错位扣掉再宣称“误差只有 0.08 mm”，就隐藏了回放真正存在的时间误差。

## 结果：插值更密，不等于时间更准

统一计算得到：

| 回放方式               | 位置拟合延迟 | 速度拟合延迟 | 未平移位置 RMSE | 平移后位置 RMSE |
| ---------------------- | -----------: | -----------: | --------------: | --------------: |
| 30 Hz 原样 `a[k]`      |    **21 ms** |        22 ms |        1.941 mm |        0.085 mm |
| 300 Hz 插值 `a[k]`     |    **38 ms** |        38 ms |        3.492 mm |        0.084 mm |
| 300 Hz 插值 `a[k+1]`   |     **4 ms** |         3 ms |        0.387 mm |        0.074 mm |
| 原始高频 `sent_action` |     **0 ms** |         1 ms |        0.095 mm |        0.095 mm |

![四种回放方式的延迟搜索曲线]({{ '/assets/img/posts/ur10e-rtde-replay/lag-comparison.png' | relative_url }})

_每个子图都扫描回放轨迹相对原始 RTDE actual 的时间平移。曲线最低点依次位于约 21、38、4 和 0 ms。_

30 Hz 原样组的 2 秒滑窗结果稳定在 20～21 ms；300 Hz `a[k]` 组稳定在 37～38 ms；`a[k+1]` 组的九个窗口全部为 4 ms；原始高频组则在 0～1 ms 之间。这说明拟合值不是由某一个局部转折偶然决定的。

更值得注意的是，前三组在扣除各自的时间平移后，位置 RMSE 都下降到约 0.07～0.09 mm。也就是说，它们生成的轨迹形状几乎相同，主要差异集中在时间轴上。问题不是“插值把路径插坏了”，而是“插值后的目标在错误的时间到达了”。

## 为什么 `a[k]` 插值会多出近一帧

300 Hz `a[k]` 回放把当前 dataset action 当作当前 33.3 ms 周期末端的目标。它虽然在周期内生成了十个平滑的中间点，却也把 action 的完整到达时间推到了周期末。增加发送点只改变了两个标签之间的运动形状，没有自动修正标签代表的时刻。

改用 `a[k+1]` 后，程序在当前周期内向下一帧目标推进。两种 300 Hz 方法的拟合延迟相差 34 ms，接近一个 30 Hz 帧周期的 33.3 ms。这是本次实验中最直接的证据：决定结果的是帧级 action 对齐，而不是 300 Hz 这个数字本身。

不过，`a[k+1]` 不应被泛化成所有策略都要“向前移动一帧”。离线回放已经知道整段未来 action，因此可以这样重排；在线策略能否使用下一时刻目标，取决于模型输出的是单步 action、action chunk，还是带有明确执行时刻的轨迹。正确做法是先定义标签语义，再让推理与执行遵守同一时间契约。

原始高频回放表现最好也有同样的原因。它不仅提高了频率，还保留了示范时真正提交给控制接口的连续目标和原始发送节奏。30 Hz dataset 在采样时已经丢弃了帧间的大量控制更新，事后插值只能构造一条平滑曲线，不能唯一恢复那些曾经实际发送过的命令。

## 两种 target，两个完全不同的“延迟”

原始记录还揭示了另一个容易误读的现象。把同一 RTDE 流中的内部 `target_TCP_pose` 与 `actual_TCP_pose` 比较，联合 XYZ 位置拟合约为 **0 ms**，分轴和速度结果为 0～1 ms，未平移位置 RMSE 约为 0.090 mm。

但把外部遥操作 `sent_action` 映射到 RTDE 时间后，再与原始 `actual_TCP_pose` 比较，位置拟合约为 **101 ms**，速度拟合约为 **93 ms**。

![外部 sent_action、RTDE 内部 target 与 actual 的关系]({{ '/assets/img/posts/ur10e-rtde-replay/source-target-actual.png' | relative_url }})

_外部 sent_action 明显领先；RTDE 内部 target 与 actual 在这次轨迹中几乎重合。两种 target 位于控制链路的不同位置。_

约 100 ms 描述的是外部目标到实际反馈之间的整体动态关系，其中可能包含接口处理、轨迹生成、限速、滤波和机械响应。RTDE 内部 target 已经是控制器生成的内部轨迹目标，而且与 actual 使用同一个机器人时钟。把两者都简称为“action”或“target”，就会错误地把外部目标的动态滞后归到 RTDE 内部 target 上。

位置拟合的 101 ms 与速度拟合的 93 ms 也不完全一致，说明这段响应不是严格的单一固定时间平移。现有材料不能把约 100 ms 唯一归因于 `lookahead_time`、servo gain 或某一个控制环参数。

## `0 ms` 不代表机器人瞬时响应

原始高频回放相对原始实际轨迹得到 0 ms，不代表机器人收到 action 后可以瞬时到达目标。原始示范和回放都经过相似的控制器与机械系统动态；只要输入时序足够接近，两次运行就可能产生几乎重合的实际响应。

同样，1 ms 是延迟搜索步长，不是经过标定的同步精度。主机与机器人时钟通过缓存控制器时间读取前后的主机中点做近似关联，缓存年龄和传输耗时并没有被精确测量。因此更准确的表述是：**在当前分析分辨率与同步条件下，没有检测到高频回放相对原始轨迹的明显额外延迟。**

亚毫米 RMSE 也只表示同一任务、相似初始条件下的相对轨迹复现误差，不能当作 UR10e 的绝对定位精度或完整时空标定精度。

## 对机器人数据采集与回放的启示

这次实验给出了几条直接的工程启示。

第一，录制训练数据时，应尽量同时保存高频控制事件。低频 dataset 可以服务训练，但独立的控制日志保留了帧间真正发生的命令，为之后检查标签语义、重建回放和分析动态提供了依据。

第二，数据格式需要说明 action 的生效时刻。只写“30 Hz action”是不够的，还要说明它来自当前观测之前还是之后、是当前周期起点还是终点目标、控制器在两帧间如何保持或插值。

第三，评估回放要把时间误差和形状误差分开。未平移误差回答“实际复现得怎样”，平移后误差回答“如果只看轨迹形状是否一致”。两者同时报告，才能看出 300 Hz `a[k]` 的主要问题是时间对齐而不是路径形状。

第四，比较前必须固定参考信号。dataset state、外部 `sent_action`、RTDE 内部 target 和 RTDE actual 分别处在不同的数据链路或控制阶段；名称相似不代表物理含义相同。

第五，插值策略应该来自部署语义，而不是只追求更高频率。对于在线策略，可能需要预测未来 action chunk 并为每个点附带执行时刻；对于离线回放，则可以直接保存和重放原始高频命令。无论采用哪种方式，都应让训练标签、推理输出和执行调度共享同一时间定义。

## 结论与边界

在这次单 episode、每种方法各一次成功回放的 UR10e 实验中，30 Hz 原样回放产生约 21 ms 的相对延迟；把当前帧 action 插值到 300 Hz 后，延迟增加到 38 ms；改用下一帧 action 后下降到 4 ms；保留原始约 500 Hz 指令及发送间隔时，实际轨迹最接近原始示范。

最重要的结论不是“300 Hz 不好”，也不是“所有 action 都应该前移一帧”，而是：

> **频率决定一秒发送多少次，时间语义决定每次发送的目标属于什么时候。只有两者同时正确，高频回放才真正有意义。**

这些数字仍受单次运行、初始内部状态、设备条件、时钟近似映射和具体轨迹影响。要判断结论能否推广，下一步需要对多条轨迹、多次重复运行和不同速度范围进行统计，并使用更严格的主机—机器人时钟标定。相机链路也需要单独的曝光时间与同步测量，不能从 dataset timestamp 直接推断。
